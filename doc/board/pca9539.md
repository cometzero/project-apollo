# PCA9539 board component 검증

Apollo QVP의 기존 Linux `gpio-pca953x` 드라이버로 SystemC PCA9539를
제어한다. 별도 Linux 드라이버나 board manager는 추가하지 않는다.
PCA9535에는 RESET 핀이 없으므로 RESET_N을 제공하는 PCA9539를 사용한다.
Register/reset/INT 기준은 [TI PCA9539, SCPS130H Rev. H](https://www.ti.com/lit/ds/symlink/pca9539.pdf)이다.

## 연결

| 연결 | 구성 |
| --- | --- |
| I2C controller | DW APB I2C0, 기존 MMIO `0x30100000` |
| I2C targets | 기존 EEPROM `0x50`, PCA9539 `0x74` |
| RESET_N | SMD PL061 GPIO0 출력 → PCA9539, active-low |
| INT_N | PCA9539 → SMD PL061 GPIO1 입력, active-low |
| PL061 AP alias / IRQ | `0x40750000`, SPI 193 / architectural INTID 225 |
| GPIO loopback | PCA9539 P00 → P01, P10 → P11 |

추가 AP MMIO나 GIC SPI를 할당하지 않는다. PL061 GPIO0/1 pull-up으로
reset 해제와 interrupt idle을 표현한다. PCA9539 GPIO input 기본값은 low다.

배선은 [board/pca9539.lua](../../hsoc-stack/tools/qbox-platform/platforms/apollo/board/pca9539.lua)에
분리했다. SoC controller의 CCI 경로와 다른 I2C port의 EEPROM은 유지한다.
Kernel의 [apollo-qvp-board.dtsi](../../hsoc-stack/components/primary_compute/linux/arch/arm64/boot/dts/arm/apollo-qvp-board.dtsi)는
같은 연결을 기술한다. `GPIO_PCA953X`, `GPIO_PCA953X_IRQ`, `I2C_CHARDEV`를
활성화하고 BSP에 `libgpiod-tools`, `i2c-tools`를 포함한다.

## 실행

Workspace root에서 BSP를 빌드하고 별도 시험용 디스크로 부팅한다.

```bash
./yocto_build.sh --bsp
./run_qbox_yocto.sh --bsp --headless --keep-running-after-pass \
  --timeout 600 --copy-disks --no-persistent-rse-state \
  --out-dir build/qbox-apollo-qvp/pca9539-runtime
ssh -p 8022 root@127.0.0.1 'sh -s' < scripts/test/verify_qbox_pca9539.sh
```

시험은 driver binding, GPIO 16개, reset 중 I2C NACK, reset register defaults,
두 bank GPIO readback, rising/falling event와 PL061 IRQ counter 증가를 검사한다.
Reset 시험 전 드라이버를 unbind하고, 시험 후 reset 및 rebind하여 regcache와
하드웨어 상태를 일치시킨다. 정상 종료 marker는
`APOLLO_PCA9539|v=1|event=final|status=PASS`다.
GPIO0/1과 PCA loopback pin을 사용하는 다른 프로그램 없이 실행한다.

## 모델 범위

I2C는 기존 `dw_i2c_extension`의 byte transaction/repeated START/STOP을
사용한다. 공유 bus는 target의 address-NACK에 따라 순서대로 전달하므로
각 target은 다른 주소 요청에 부작용을 발생시키지 않아야 한다.
주소 충돌 감지, multi-controller arbitration, SCL/SDA bit timing은 구현하지 않는다.

GPIO는 fixed single-driver bool 연결이다. INT_N은 pull-up이 있는 open-drain의
논리 레벨을 표현하지만 전압, 다중 출력 충돌, 전기적 net resolution은 모델링하지
않는다. RESET_N low 동안 register reset과 I2C NACK을 제공하며 reset pulse 폭과
아날로그 power-on timing은 검증하지 않는다. GPIO output-enable 신호는 별도로
제공하며, 이번 loopback은 입력 모드에서 외부 input level을 전달한다.

QEMU GPIO 출력에서 SystemC target으로 넘어가는 신호는 `run_on_sysc` 큐에
대기 없이 전달한다. QEMU 초기화/reset을 기다리는 SystemC thread에 다시
동기 콜백을 요청하면 교착되기 때문이다. 같은 QEMU instance 내부 연결의
직접 전달 경로는 유지한다. PL061 pull-up과 runtime reset 회귀 시험으로
이 경계를 검사한다.

| Lua wiring 및 기존 map parser | 4 PASS, `board-tests.log` |
| DW I2C/PCA9539 SystemC | 2 CTest targets / 6 scenarios PASS, `systemc-tests.log` |
| PL061 초기화/runtime reset 회귀 | PASS, `pl061-reset-test.log` |
| Kernel configure/compile | PASS, `kernel-compile-recovery.log` |
| BSP build (`./yocto_build.sh --keep-conf --bsp`) | PASS, `bsp-gpio-fix-build.log` |
| Provider `do_check` | 45 PASS, `provider-gpio-fix-tests.log` |
| BSP 부팅 | `runtime-fixed/result.json`: `passed=true` |
| Linux PCA9539 시험 | 연속 2회 PASS, `guest-test-4.log`, `guest-test-repeat.log` |

Linux에서 `gpiochip1 [0-0074] (16 lines)`와 `pca953x` binding을 확인했다.
PL061 GPIO0 low에서 I2C NACK, 해제 후 output=`ffff`, polarity=`0000`,
configuration=`ffff`를 확인했다. 두 bank loopback은 high=`1 1`, low=`0 0`이며,
각 실행에서 rising 2개/falling 2개를 받았다. PL061 GPIO1의 Linux IRQ 47
counter는 `12→16`, 재실행에서는 `22→26`으로 증가했다. 같은 I2C0의 EEPROM
첫 16바이트는 두 실행 모두 reset 전후 동일했다. 시험 후 driver rebind도 성공했다.

GIC INTID 225는 DT/Lua 배선 값이다. 이 커널의 `/proc/interrupts`에는 chained
GIC parent가 표시되지 않아, 실제 PCA9539를 서비스하는 PL061 hwirq 1의
counter를 관찰했다. GIC 225의 별도 raw counter 증가를 검증했다고 주장하지 않는다.

초기 kernel build 실패는 독립 DT 검사가 활성 build directory의 compiler
설정을 덮어쓴 작업 충돌이었다. Yocto configure/compile 직렬 재실행으로
복구했다. 초기 QBox 실행은 GPIO 동기 콜백 교착으로 실패했고 공용 signal
socket 수정 후 재부팅했다. 이전 실패 로그도 보존한다.

이번 결과는 board component 범위다. 전체 coverage audit는
`ap_9_1_1_memory_map: not_available`, `G1: not_run`으로 FAIL이며 전체 FVP
동등성을 의미하지 않는다. DT schema 검사는 로컬 `dtschema` 버전 부족으로
실행되지 않았다. 전기적 timing과 multi-controller I2C는 검증 범위 밖이다.
