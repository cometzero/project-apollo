1024 B도 같은 3.4375 평균을 보였다. 당시 source-derived였던 1024-B 배치는 후속
actual config와 일치한다. 이 계산은 guest PFN·실제 요청 순서·혼잡을 관측하지 않으므로
bandwidth 원인을 확정하지 않는다. Channel-local packed address 열도 세 stripe에서
같아 큰 stripe 자체의 row locality 개선을 가정할 수 없다.

## Independent mesh clock의 통계 reset 결함

Counter 의미를 대조하던 중 `GarnetNetwork::collateStats()`가 network의 `curCycle()`에서
RubySystem domain의 reset cycle을 빼는 것을 확인했다. 두 clock이 다르고 reset tick이
0보다 크면 같은 시간 단위가 아니다. 기존 native로 1 ms warmup 뒤 stats reset과 64-read
traffic를 실행했을 때 동일 2-GHz control은 통과했지만 mesh 1 GHz는 `m5.stats.dump()`에서
`ValueError: RHS cycle value larger than LHS`로 실패했다.

기존 6-case directed framing은 tick 0에서 시작했고 nonzero reset을 하지 않았으므로
traffic 진행과 packet/flit 검증의 PASS는 유지하지만 Linux ROI reset 지원의 근거는 아니다.
원본 binary·source·명령·실패 log는 `counter-reset-probe/`와
`reports/garnet-stats-reset-diagnosis.json`에 보존했다. 수정은 network-local cycle epoch와
repeated dump 시 link/VC counter 재계산으로 한정했다. Yocto native rebuild는
**815 tasks 성공, 9개 재실행, 212.3227 s**로 완료했다
(`build-native-stats-reset/yocto.log`, `build-native-stats-reset/result.json`).

새 native의 `mesh-2ghz`, `mesh-1ghz`, `mesh-4ghz`와
`original-mesh1-reproduction` 네 가지 검사는 모두 `PASS`다. 앞의 세 검사는 nonzero
reset 이후 zero-elapsed 값, 64 reads/4096 bytes 완료와 repeated dump의 network-local
분모·counter 재계산을 확인했다. 원본 mesh1 재현 조건도 raw config 차이 없이
return code 1→0으로 바뀌었다. 상세 결과는
`garnet-stats-fixed/`와 `reports/garnet-stats-native-verification.json`에 있다.
이는 **native Garnet 통계 검증**이다. 당시 남아 있던 FS split-clock 검증 중 mesh1GHz와
Ruby/system1GHz first ROI는 아래 후속 완료 기록에서 별도로 확인했다.
새 binary는 v4의 별도 pinned input과 fresh matching snapshot을 사용하며 기존 snapshot
contract를 우회하지 않는다. Runtime DVFS와 Router buffer repeated-dump 동작은
이번 수정·검증 범위에 포함하지 않는다.

V4 binary로 기존 matching backend 4개와 framing 6개도 새 output에 재실행했다.
모두 `PASS`이며 run-local output 경로만 정규화한 config, 선택한 traffic/counter/latency
값이 이전 실행과 일치했다. Backend는 supply 종료 후 source/DRAM completed bytes의

실제 `640×480` synthetic RGB normalization이며 Autonomous Driving application FPS를
뜻하지 않는다. 16 channels 모두 양의 read/write service를 기록했다. Cache/DRAM 후보와
비교하기 전 warmup 및 측정 길이를 각각 바꾸어 안정성을 확인한다. 실행시간을 줄이기 위해
원본 frame 크기나 output 검증을 생략하지 않았다.

CPU0의 committed instructions는 23,359,838개이고 다른 core에서도 합계 878,973개를
관측했다. 이 실행은 thread affinity를 설정했지만 CPU isolation·IRQ affinity를 따로
설정하지 않았다. 동적 IRQ mask는 수집하지 않았다. 따라서 cache/NoC/DRAM counter는
Linux housekeeping을 포함한다. `reports/image-baseline-counter-context.json`에 counter
경로와 단위를 기록했다. Garnet 평균 latency는 gem5 ticks이며 mesh cycles가 아니다.

`campaign-v2.json`은 원본 39개 case와 40개 comparison을 보존하고 baseline pool 1
재사용 case 및 pool 2와의 비교를 추가한 revision이다. 총 40개 case, 41개 comparison이며
새 case는 아직 `NOT_RUN`이다. 같은 hardware의 matching snapshot을 재사용한다. 두 조건은
buffer pool 크기와 그에 따른 working set이 함께 달라지므로 hardware 단일 변수 효과로
해석하지 않는다. 이후 `campaign-v3.json`은 Schema 3과 image warmup 2→4회 조건을
반영했으며 해당 queue는 active child 완료 후 종료했다. 현재 실행 중인 registry는
`campaign-v4.json`이다. **40 cases / 19 snapshots / 41 comparisons**와 profile,
workload, tolerance, target policy를 유지하고 새 native로 모든 측정 입력을 분리한다.
이전 registry·snapshot·실행 결과는 보존한다. P5의 같은/다른 cluster background와
P6 shortlist robustness는 여전히 남아 있다.

## Native 경로의 별도 진단

이전 계약의 read pilot(`runs/read-w16-p2-wu1-s64`)도 checksum 16,777,216과 guest 종료를
확인했다. 16 workers, 64 MiB, measured 2 passes의 native ROI는 **3.2812175 ms**,
useful **40.904856 GB/s**, DRAM **41.309037 GB/s**였다. Host 전체 시간은
**4,397.871 s**였다. `reports/read-pilot-completed.json`에 기록한 raw `VALID` /
`HISTORICAL_LIMITED` 결과다. V3 dependency-bound read16 baseline에서 guest/application/
DRAM/cache 및 worker instruction의 선택한 raw 값을 동일하게 재현했다
(`reports/read-schema3-baseline-completed.json`). 이전 provenance를 승격하거나 read
warmup/length 수렴을 입증한 것은 아니다. V4에서는 새 native에서 다시 측정한다.

이전 dependency 계약의 read pilot와 image warmup 1/2회 실행에서 launcher가 기록한
첫 UART까지의 host 시간은 각각
24.397 / 24.628 / 24.994 s다. `boot-timings.json`에는 이 경계만 있으므로 Atomic 초기화,
O3 warmup, ROI, output 검증 각각의 host 소요시간은 분리할 수 없다. 이 값은 snapshot
복원 후 첫 UART까지의 시간이며 fresh Linux boot 시간이나 simulated latency가 아니다.
후보 수에 단일 pilot 시간을 곱한 값을 확정 완료 시각으로 사용하지 않는다.

V4 image ROI/read warmup 중 host 관측에서는 gem5 process별 RSS가 약 3.55/4.07 GiB,
host 가용 memory가 약 4.55 GiB였다. 두 process의 native thread 수는 각각 1개였고
16-CPU host의 load average는 약 2.13이었다. 이 시점의 resource 관측을 근거로 동시 FS
실행은 2개를 유지한다(`reports-v4/host-resource-observation.json`). 이는 실행 중 한 시점의
RSS이며 최종 peak나 모든 profile의 memory 요구량, simulated 성능을 뜻하지 않는다.

Matching native backend의 40 µs window read service는 direct/fanout **255.8464 GB/s**,
single width32 **42.6864 GB/s**, single width256 **63.9696 GB/s**다. 모든 요청은 supply 종료 후
drain까지 완료했다. 두 input 구조가 다르므로 비율을 CPU/CHI 손실률로 바꾸지 않는다.
Native `NoncoherentXBar`는 response port별 layer를 사용하고, 64-B payload의 layer 점유는
`1 + ceil(64/width)` cycles다. 2 GHz에서 single port의 약 42.67/64 GB/s 상한과 일치하는
진단이다. Detailed artifacts는 `native-backend-matched/`, 비교는
`reports/native-backend-matched.json`에 있다.

Directed framing은 각 조건에서 64 completed reads/4096 bytes를 확인했다.
Width32의 DAT 512 packets/1024 flits가 width16에서 1024/2048로 바뀌었다.
`directed-framing/summary-6cases.json`의 request response 평균은 baseline 228.242 ns,
CPU1 239.711 ns, mesh1 318.977 ns, CPU1×mesh1 319.820 ns,
Ruby1 241.570 ns, width16 248.336 ns다. 이는 CPU instruction 실행 없이 private cache/
Ruby/Garnet/DRAM을 통과한 controlled request의 관측이며 image latency가 아니다.

## 실행과 분석 방법

기존 launcher의 command 경로를 사용한다. 자체 marker가 있는 image workload에
`gem5-control run`을 중첩하지 않는다.

```sh
./run_gem5_linux.sh --headless --cpus 16 --channels 16 \
  --resume SNAPSHOT --workload command \
  --command '/usr/bin/apollo-image-bench --width 640 --height 480 --frames 4 --frame-pool 2 --warmup 4 --cpu 0' \
  --out-dir NEW_RUN --timeout 86400

python3 scripts/gem5/soc_spec.py inventory NEW_RUN --output NEW_INVENTORY.json
python3 scripts/gem5/soc_spec.py report CAMPAIGN.json --output NEW_REPORT.json
```

실제 campaign에서는 pinned `--deploy-dir`와 matching `--profile`도 함께 지정한다.
위 warmup 4회/frames 4는 v4 baseline의 warmup 2→4회와 frames 4→8 수렴 gate를
통과한 screening 조건이다. 이 승인은 해당 baseline workload에 한정하며, 다른 후보나
동시 부하 조건의 수렴을 대신하지 않는다.
Foreground timestamp는 CNTVCT이고 전체 ROI는 gem5 ticks다. Collector는 configured counter
frequency를 대조하고 두 시간을 분리한다. Final pool 전체의 output을 검증하며 각 과거 frame의
출력을 따로 보존했다고 주장하지 않는다. 적은 frame sample의 maximum은 WCET/p99가 아니다.

최종 제품 사양·PPA·capacity 판정은 현재 입력에서 `UNDECIDED`다. 실행 가능한 모델 후보의
상대 성능과 bottleneck evidence를 얻는 작업은 계속 진행한다.
