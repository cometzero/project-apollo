# ​D20.1 About the RAS Extension

Source: <https://developer.arm.com/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-1-About-the-RAS-Extension>

#### D20.1 About the RAS Extension

I LBKPL
:   The RAS Extension extends the exception syndrome registers to include fields that allow the PE to report a [PE error state](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-4-Taking-error-exceptions?lang=en#mdterm_pe_error_state) when an [Error exception](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-3-Generating-error-exceptions?lang=en#mdterm_error_exception) is taken.

I THGHB
:   The RAS Extension defines System registers that are specific to RAS, including to access optional Error records defined by the RAS System Architecture. The format of the error record registers is defined in [Error record System register view](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-7-Error-records-in-the-PE/-D20-7-1-Error-record-System-register-view?lang=en#mdsec_error_record_system_register_view).

R YWXWL
:   The RAS Extension does not prescribe the level of reliability, availability, and serviceability in the PE. The RAS features that the system and PE include, for example to detect, correct, contain, or defer errors, are IMPLEMENTATION DEFINED. The RAS Extension defines a framework for building RAS features in a PE.

    > Example D20-1 Minimal implementation of RAS Extension
    >
    > For systems without a requirement for high reliability and availability, a minimal approach to RAS might include:
    >
    > - There is no error detection. ERRIDR\_EL1.NUM is zero, indicating that no error records are implemented. See [Error record System register view](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-7-Error-records-in-the-PE/-D20-7-1-Error-record-System-register-view?lang=en#mdsec_error_record_system_register_view).
    > - Any error [signaled](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A1-Introduction-to-the-Arm-Architecture/-A1-7-Reliability--Availability--and-Serviceability/-A1-7-3-General-taxonomy-of-errors?lang=en#mdterm_ras_signal) to the PE generates an asynchronous SError exception, and on taking the SError exception:
    >
    >   - The PE error state is recorded as [Uncontainable (UC)](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-4-Taking-error-exceptions/-D20-4-2-PE-error-state-classification?lang=en#mdterm_uncontainable_pe_error).
    >
    >     - If [FEAT\_RASv2](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A2-A-profile-Architecture-Extensions/-A2-2-Armv8-A-architecture-extensions/-A2-2-10-The-Armv8-9-architecture-extension?lang=en#feat_feat_rasv2) is implemented, then [ESR\_ELx](/documentation/ddi0487/mc/-Part-K-Appendixes/-Appendix-K14-Registers-Index/-K14-1-Introduction-and-register-disambiguation/-K14-1-2-Register-name-disambiguation-by-Exception-level?lang=en#esr_elx).VFV is set to 0, meaning [FAR\_ELx](/documentation/ddi0487/mc/-Part-K-Appendixes/-Appendix-K14-Registers-Index/-K14-1-Introduction-and-register-disambiguation/-K14-1-2-Register-name-disambiguation-by-Exception-level?lang=en#far_elx) is UNKNOWN and not valid. If [FEAT\_RASv2](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A2-A-profile-Architecture-Extensions/-A2-2-Armv8-A-architecture-extensions/-A2-2-10-The-Armv8-9-architecture-extension?lang=en#feat_feat_rasv2) is not implemented, then [FAR\_ELx](/documentation/ddi0487/mc/-Part-K-Appendixes/-Appendix-K14-Registers-Index/-K14-1-Introduction-and-register-disambiguation/-K14-1-2-Register-name-disambiguation-by-Exception-level?lang=en#far_elx) is always UNKNOWN and not valid on taking an SError exception.
    >   - [FEAT\_PFAR](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A2-A-profile-Architecture-Extensions/-A2-2-Armv8-A-architecture-extensions/-A2-2-10-The-Armv8-9-architecture-extension?lang=en#feat_feat_pfar) is not implemented, meaning [ESR\_ELx](/documentation/ddi0487/mc/-Part-K-Appendixes/-Appendix-K14-Registers-Index/-K14-1-Introduction-and-register-disambiguation/-K14-1-2-Register-name-disambiguation-by-Exception-level?lang=en#esr_elx).PFV is set to 0.
    >
    >   See [Taking error exceptions](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-4-Taking-error-exceptions?lang=en#mdsec_taking_error_exceptions).
    > - The [`ESB`](/documentation/ddi0487/mc/-Part-C-The-AArch64-Instruction-Set/-Chapter-C6-A64-Base-Instruction-Descriptions/-C6-2-Alphabetical-list-of-A64-base-instructions/-C6-2-159-ESB?lang=en#isa_esb) instruction is implemented as `NOP`.
    >
    >   See also [ESB and virtual SError exceptions](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-5-Error-synchronization-event/-D20-5-1-ESB-and-virtual-SError-exceptions?lang=en#mdsec_esb_and_virtual_serror_exceptions) and [ESB and delegated SError exceptions](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-5-Error-synchronization-event/-D20-5-2-ESB-and-delegated-SError-exceptions?lang=en#mdsec_esb_and_delegated_serror_exceptions).

    > Example D20-2 Minimal implementation of RAS Extension
    >
    > For systems without a requirement for high reliability and availability, a minimal approach to RAS might include:
    >
    > - There is no error detection. ERRIDR\_EL1.NUM is zero, indicating that no error records are implemented. See [Error record System register view](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-7-Error-records-in-the-PE/-D20-7-1-Error-record-System-register-view?lang=en#mdsec_error_record_system_register_view).
    > - Any error [signaled](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A1-Introduction-to-the-Arm-Architecture/-A1-7-Reliability--Availability--and-Serviceability/-A1-7-3-General-taxonomy-of-errors?lang=en#mdterm_ras_signal) to the PE generates an asynchronous SError exception, and on taking the SError exception the PE error state is recorded as [Uncontainable (UC)](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-4-Taking-error-exceptions/-D20-4-2-PE-error-state-classification?lang=en#mdterm_uncontainable_pe_error).
    >
    >   See [Taking error exceptions](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-4-Taking-error-exceptions?lang=en#mdsec_taking_error_exceptions).
    > - The [`ESB`](/documentation/ddi0487/mc/-Part-C-The-AArch64-Instruction-Set/-Chapter-C6-A64-Base-Instruction-Descriptions/-C6-2-Alphabetical-list-of-A64-base-instructions/-C6-2-159-ESB?lang=en#isa_esb) instruction is implemented as `NOP`.
    >
    >   See also [ESB and virtual SError exceptions](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-5-Error-synchronization-event/-D20-5-1-ESB-and-virtual-SError-exceptions?lang=en#mdsec_esb_and_virtual_serror_exceptions) and [ESB and delegated SError exceptions](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-5-Error-synchronization-event/-D20-5-2-ESB-and-delegated-SError-exceptions?lang=en#mdsec_esb_and_delegated_serror_exceptions).

    > Example D20-3 Common error handling for RAS features
    >
    > For a system with a requirement for high reliability and error containment:
    >
    > - When errors are detected, they are recorded in error records. This includes both correctable and uncorrectable errors. Error correction and detection logic exists on all significant memory structures, and might include other non-memory structures.
    > - Most uncorrectable errors generate poison values to defer the error.
    > - On consuming poison from the memory system, a load instruction that would corrupt PE state generates a synchronous External Abort exception, regardless of the memory type. For systems where the performance impact of this approach might be an issue, the controls defined by [FEAT\_ANERR](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A2-A-profile-Architecture-Extensions/-A2-2-Armv8-A-architecture-extensions/-A2-2-10-The-Armv8-9-architecture-extension?lang=en#feat_feat_anerr) and [FEAT\_ADERR](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A2-A-profile-Architecture-Extensions/-A2-2-Armv8-A-architecture-extensions/-A2-2-10-The-Armv8-9-architecture-extension?lang=en#feat_feat_aderr) are provided.
    > - On taking error exceptions, the PE error state is [Recoverable state (UER)](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-4-Taking-error-exceptions/-D20-4-2-PE-error-state-classification?lang=en#mdterm_recoverable_pe_error).
    > - [FEAT\_PFAR](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A2-A-profile-Architecture-Extensions/-A2-2-Armv8-A-architecture-extensions/-A2-2-10-The-Armv8-9-architecture-extension?lang=en#feat_feat_pfar) is implemented, and the PE makes a best effort attempt to record the faulting physical address in [PFAR\_ELx](/documentation/ddi0487/mc/-Part-K-Appendixes/-Appendix-K14-Registers-Index/-K14-1-Introduction-and-register-disambiguation/-K14-1-2-Register-name-disambiguation-by-Exception-level?lang=en#pfar_elx) or MFAR\_ELx, setting [ESR\_ELx](/documentation/ddi0487/mc/-Part-K-Appendixes/-Appendix-K14-Registers-Index/-K14-1-Introduction-and-register-disambiguation/-K14-1-2-Register-name-disambiguation-by-Exception-level?lang=en#esr_elx).PFV to 1.
