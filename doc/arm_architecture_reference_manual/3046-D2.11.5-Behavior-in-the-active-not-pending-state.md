# ​D2.11.5 Behavior in the active-not-pending state

Source: <https://developer.arm.com/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D2-AArch64-Self-hosted-Debug/-D2-11-Software-Step-exceptions/-D2-11-5-Behavior-in-the-active-not-pending-state>

##### D2.11.5 Behavior in the active-not-pending state

In this state, the PE does one of the following:

- Executes the instruction to be stepped and either:

  - Completes it without taking a synchronous exception.
  - Takes a synchronous exception if the instruction generates one.
- Takes an asynchronous exception without completing execution of the instruction.
- Enters Debug state because of a *Halting debug event*.

The instruction to be stepped is usually the instruction in memory at the address specified by the PC.

However, when [FEAT\_STEP2](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A2-A-profile-Architecture-Extensions/-A2-3-Armv9-A-architecture-extensions/-A2-3-6-The-Armv9-5-architecture-extension?lang=en#feat_feat_step2) is implemented, the instruction to be stepped might be specified in [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1). See [Software Step behavior when FEAT\_STEP2 is implemented](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D2-AArch64-Self-hosted-Debug/-D2-11-Software-Step-exceptions/-D2-11-5-Behavior-in-the-active-not-pending-state?lang=en#software_step_when_feat_step2_implemented).

If the PE executes the instruction without taking any exceptions, then the PE sets [PSTATE](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D1-The-AArch64-System-Level-Programmers--Model/-D1-5-Process-state--PSTATE?lang=en#pstate).SS to 0, meaning that after the instruction has been executed:

- If the instruction has disabled debug by setting [PSTATE](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D1-The-AArch64-System-Level-Programmers--Model/-D1-5-Process-state--PSTATE?lang=en#pstate).D to 1 then software step advances to the inactive state.
- If the instruction disables software step by a direct write to a System register, for example a write to [MDSCR\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-20-MDSCR-EL1--Monitor-Debug-System-Control-Register?lang=en#reg_aarch64_mdscr_el1).KDE or [MDSCR\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-20-MDSCR-EL1--Monitor-Debug-System-Control-Register?lang=en#reg_aarch64_mdscr_el1).SS, then software step might advance to the inactive state. These writes require explicit synchronization to guarantee their effect. See [Synchronization and the software step state machine](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D2-AArch64-Self-hosted-Debug/-D2-11-Software-Step-exceptions/-D2-11-10-Additional-considerations?lang=en#bcgcdeef).
- Otherwise, software step advances to the active-pending state. See [Behavior in the active-pending state](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D2-AArch64-Self-hosted-Debug/-D2-11-Software-Step-exceptions/-D2-11-7-Behavior-in-the-active-pending-state?lang=en#bcggcbid).

If the PE takes either a synchronous or an asynchronous exception, behavior is as described in one of the following:

- [If the PE takes an exception to an Exception level that is using AArch64](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D2-AArch64-Self-hosted-Debug/-D2-11-Software-Step-exceptions/-D2-11-5-Behavior-in-the-active-not-pending-state?lang=en#bcghefge).
- [If the PE takes an exception to an Exception level that is using AArch32](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D2-AArch64-Self-hosted-Debug/-D2-11-Software-Step-exceptions/-D2-11-5-Behavior-in-the-active-not-pending-state?lang=en#bcggcjig).

If the PE enters Debug state because of a Halting debug event, behavior is as described in [Entering Debug state and Software Step](/documentation/ddi0487/mc/-Part-H-External-Debug/-Chapter-H2-Debug-State/-H2-3-Entering-Debug-state/-H2-3-6-Entering-Debug-state-and-Software-Step?lang=en#cacggbcc).

###### D2.11.5.1 If the PE takes an exception to an Exception level that is using AArch64

As part of exception entry, the PE does all of the following:

- Sets [SPSR\_ELx](/documentation/ddi0487/mc/-Part-K-Appendixes/-Appendix-K14-Registers-Index/-K14-1-Introduction-and-register-disambiguation/-K14-1-2-Register-name-disambiguation-by-Exception-level?lang=en#spsr_elx).SS to 0 or 1, depending on the exception. See [Table D2-21](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D2-AArch64-Self-hosted-Debug/-D2-11-Software-Step-exceptions/-D2-11-5-Behavior-in-the-active-not-pending-state?lang=en#tbl_cjahghje).
- It is IMPLEMENTATION SPECIFIC whether [SPSR\_ELx](/documentation/ddi0487/mc/-Part-K-Appendixes/-Appendix-K14-Registers-Index/-K14-1-Introduction-and-register-disambiguation/-K14-1-2-Register-name-disambiguation-by-Exception-level?lang=en#spsr_elx).SS is set to 0 or 1 when an SError exception is taken to ELx without completing execution of the instruction.
- Sets [PSTATE](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D1-The-AArch64-System-Level-Programmers--Model/-D1-5-Process-state--PSTATE?lang=en#pstate).SS to 0. This causes software step to enter either the active-pending state or the inactive state, depending on whether debug exceptions are enabled or disabled from the Exception level that the exception is taken to:

  Enabled
  :   Software step enters the active-pending state.

  Disabled
  :   Software step enters the inactive state.

  In either case, on taking the exception, a step is complete.
- Sets [PSTATE](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D1-The-AArch64-System-Level-Programmers--Model/-D1-5-Process-state--PSTATE?lang=en#pstate).D to 1.

###### D2.11.5.2 If the PE takes an exception to an Exception level that is using AArch32

This can happen only when all of the following is true:

- EL2 is implemented and is using AArch64, and the [Effective value](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#effective_value) of [MDCR\_EL2](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-17-MDCR-EL2--Monitor-Debug-Configuration-Register--EL2-?lang=en#reg_aarch64_mdcr_el2).TDE is 1. Because [MDCR\_EL2](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-17-MDCR-EL2--Monitor-Debug-Configuration-Register--EL2-?lang=en#reg_aarch64_mdcr_el2).TDE is 1, ELD is EL2.
- The exception is taken to EL1 using AArch32.

As part of exception entry, the PE sets [PSTATE](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D1-The-AArch64-System-Level-Programmers--Model/-D1-5-Process-state--PSTATE?lang=en#pstate).SS to 0. This causes software step to enter the active-pending state.

> #### Note
>
> - Software step always enters the active-pending state because the exception is taken to an Exception level that debug exceptions are enabled from, EL1. Debug exceptions are enabled from EL1 because ELD is EL2, and debug exceptions are always enabled from Exception levels that are lower than ELD.
> - AArch32 SPSRs have no SS bit.

###### D2.11.5.3 Software Step behavior when FEAT\_STEP2 is implemented

R VTLLV
:   When [FEAT\_STEP2](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A2-A-profile-Architecture-Extensions/-A2-3-Armv9-A-architecture-extensions/-A2-3-6-The-Armv9-5-architecture-extension?lang=en#feat_feat_step2) is implemented, executing from [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1) is enabled when all of the following are true:

    - The PE is in AArch64 state.
    - Software Step is in the active-not-pending state.
    - [MDSCR\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-20-MDSCR-EL1--Monitor-Debug-System-Control-Register?lang=en#reg_aarch64_mdscr_el1).EnSTEPOP is 1.
    - Either EL3 is not implemented or [MDCR\_EL3](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-18-MDCR-EL3--Monitor-Debug-Configuration-Register--EL3-?lang=en#reg_aarch64_mdcr_el3).EnSTEPOP is 1.
    - Any of the following apply:

      - EL2 is not implemented.
      - EL2 is disabled in the current Security state.
      - [MDCR\_EL2](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-17-MDCR-EL2--Monitor-Debug-Configuration-Register--EL2-?lang=en#reg_aarch64_mdcr_el2).EnSTEPOP is 1.

    Otherwise, executing from [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1) is disabled.

I WTPKX
:   The pseudocode function [`SoftwareStepOpEnabled`](/documentation/ddi0487/mc/-Part-J-Architectural-Pseudocode/-Chapter-J1-A-profile-Architecture-Pseudocode/-J1-4-Shared-pseudocode/-J1-4-135-SoftwareStepOpEnabled?lang=en#asl_func_softwarestepopenabled_0)`()` returns TRUE when executing from [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1) is enabled and FALSE otherwise.

I SFGGB
:   When executing from [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1) is disabled, the value in [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1) is ignored.

R KPFLX
:   When executing from [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1) is enabled, the instruction to be stepped is specified by the value of [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1). That is, the PE executes an instruction from [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1) instead of executing an instruction from memory.

R XTKVL
:   When the PE executes an instruction from [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1), all of the following apply:

    - The instruction address in the PC is checked by the PE as if the instruction is fetched from memory.

      For example, the instruction might generate any of the following exceptions based on the current value of PC:

      - PC alignment fault exception.
      - Instruction abort exception.
      - Breakpoint exception.
    - A read of PC by the instruction returns the current value of PC.
    - A write to PC updates the PC as normal.

I RJMRP
:   In [RXTKVL](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D2-AArch64-Self-hosted-Debug/-D2-11-Software-Step-exceptions/-D2-11-5-Behavior-in-the-active-not-pending-state?lang=en#xtkvl), reads of the PC includes indirect reads in the event of an exception or debug event being taken, as follows:

    - If the instruction execution causes a synchronous exception, or is preempted by an asynchronous exception, then the preferred return address for the exception is based on the current PC value.
    - If the instruction execution causes a synchronous entry to Debug state, or is preempted by an asynchronous entry to Debug state, then the preferred restart address for the debug event is based on the current PC value.

I VXWNT
:   When the PE executes an instruction from [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1), it is CONSTRAINED UNPREDICTABLE whether the PE fetches an instruction from the memory location addressed by the current PC. This means that, in the case where the instruction fetch would generate a synchronous External abort, it is CONSTRAINED UNPREDICTABLE whether this exception will be generated. In the case where the instruction fetch would generate a synchronous External abort on a translation table fetch or translation table update, then the exception is generated because [RXTKVL](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D2-AArch64-Self-hosted-Debug/-D2-11-Software-Step-exceptions/-D2-11-5-Behavior-in-the-active-not-pending-state?lang=en#xtkvl) requires that the translation table is checked.

    If the PE does fetch an instruction from the memory location addressed by the current PC, then that instruction is ignored.

I LYLNF
:   Instruction execution properties that are derived from the current PC value use the same method whether the PE executes an instruction from [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1) or from memory. For example, instruction execution properties that are derived from the PC being in a guarded page.

> #### Note
>
> Execution from [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1) is not considered concurrent modification and execution of instructions. Tracing properties and performance monitoring of instruction execution from [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1) are unchanged.

R DQFDD
:   The `MOVPRFX` instruction execution from [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1) does not pair with another instruction.

I RDLQR
:   If a `BRK` instruction that is prefixed by a `MOVPRFX` instruction generates a Breakpoint Instruction exception then the [ELR\_ELx](/documentation/ddi0487/mc/-Part-K-Appendixes/-Appendix-K14-Registers-Index/-K14-1-Introduction-and-register-disambiguation/-K14-1-2-Register-name-disambiguation-by-Exception-level?lang=en#elr_elx) points to the PC of `BRK` instruction and the `MOVPRFX` instruction is required to have updated the architectural state. The debugger can use [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1) to execute the original instruction that was replaced by the `BRK` instruction.

I XLQPG
:   Executing an instruction from [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1) is an indirect read of [MDSTEPOP\_EL1](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D24-AArch64-System-Register-Descriptions/-D24-3-Debug-System-registers/-D24-3-22-MDSTEPOP-EL1--Monitor-Debug-Step-Opcode-Register?lang=en#reg_aarch64_mdstepop_el1).
