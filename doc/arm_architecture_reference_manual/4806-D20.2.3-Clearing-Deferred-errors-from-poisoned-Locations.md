# ​D20.2.3 Clearing Deferred errors from poisoned Locations

Source: <https://developer.arm.com/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-2-PE-error-handling/-D20-2-3-Clearing-Deferred-errors-from-poisoned-Locations>

##### D20.2.3 Clearing Deferred errors from poisoned Locations

###### D20.2.3.1 Poison-atomicity of Memory Write Effects

D YQQLJ
:   A Memory Write Effect is *poison-atomic* if the Memory Write Effect removes a [Deferred error](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_deferred_error) ([poison](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A1-Introduction-to-the-Arm-Architecture/-A1-7-Reliability--Availability--and-Serviceability/-A1-7-3-General-taxonomy-of-errors?lang=en#mdterm_ras_poisoned)) at all Locations written to by the Memory Write Effect.

R XVFDG
:   For each store instruction with Explicit Memory Write Effects, it is IMPLEMENTATION DEFINED whether the Memory Write Effects are poison-atomic for a region of physical memory. This includes the `DC ZVA` and/or `DC GZVA` instructions.

R QSBKL
:   If a Location in a region of physical memory supports the poison-atomic property for a store instruction, then all Locations in the same naturally-aligned region support this for the same store instruction, where the size of the region is the largest translation granule that the PE supports.

I CSJLP
:   Support for the poison-atomic property for a store instruction is a property of both the PE as well as the system. That is, if the system includes a PE that supports the poison-atomic property for the instruction, then both the PE and the system support this instruction such that it is guaranteed to be poison-atomic.

    For example, the system should not split cache line writes of data to be smaller than the [poison granule](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_poison_granule) of the downstream component in order to preserve poison-atomicity of a `DC {G}ZVA` instruction.

I ZRSSM
:   There is no architected means to discover the poison-atomic property for `DC ZVA` or `DC GZVA` for any region of physical memory.

I NXNTY
:   When a Memory Write Effect to a Location is not poison-atomic, the Memory Write Effect propagates a [Deferred error](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_deferred_error) previously at the Location to the new value being written.

    > Example D20-8
    >
    > A region of physical memory uses Error Correction Codes (ECC) to provide error detection and correction. The [protection granule](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_protection_granule) for this region of memory is the size of a range covered by a single ECC. The ECC is also used to encode a [poison](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A1-Introduction-to-the-Arm-Architecture/-A1-7-Reliability--Availability--and-Serviceability/-A1-7-3-General-taxonomy-of-errors?lang=en#mdterm_ras_poisoned) value. This means the [poison granule](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_poison_granule) is the same size as the [protection granule](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_protection_granule), for this region of physical memory.
    >
    > A write that is smaller than the [protection granule](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_protection_granule) to this region of physical memory must read the [protection granule](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_protection_granule) containing the Location being written in order to calculate a new ECC for the [protection granule](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_protection_granule). If the [protection granule](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_protection_granule) contains [poison](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A1-Introduction-to-the-Arm-Architecture/-A1-7-Reliability--Availability--and-Serviceability/-A1-7-3-General-taxonomy-of-errors?lang=en#mdterm_ras_poisoned), then a [poisoned](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A1-Introduction-to-the-Arm-Architecture/-A1-7-Reliability--Availability--and-Serviceability/-A1-7-3-General-taxonomy-of-errors?lang=en#mdterm_ras_poisoned) value is written back, meaning the write is not poison-atomic.
    >
    > If a write overwrites the entire [protection granule](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_protection_granule), then the system can calculate a new ECC for the [protection granule](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_protection_granule) without reading the previous contents, meaning the write can be poison-atomic.

I GLFCV
:   A system might require software to stop using the [protection granule](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_protection_granule) until the [Deferred error](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_deferred_error) can be removed.

    For example, by not using the physical page containing the granule until the system is reset. The architecture does not set any limit on the size of a [protection granule](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_protection_granule), and it might be larger than a translation granule.

I HPJFJ
:   The size of the [poison granule](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_poison_granule) is IMPLEMENTATION DEFINED and might vary from moment to moment, instruction to instruction, and by Location. The size of the [poison granule](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_poison_granule) might be the same as the size of the [protection granule](/documentation/ddi0487/mc/-Part-K-Appendixes/Glossary?lang=en#glossdef_protection_granule), but this is not guaranteed. See also [RWLTPV](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D20-RAS-PE-Architecture/-D20-2-PE-error-handling/-D20-2-1-PE-error-detection?lang=en#wltpv).

I CBCMK
:   The regions of physical memory that support the poison-atomic property are IMPLEMENTATION DEFINED. Systems might have multiple physical memory types, including multiple physical memory regions used for bulk memory.

###### D20.2.3.2 Removing poison

I VZRKL
:   For guidance on mechanisms that software can use to remove [poison](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A1-Introduction-to-the-Arm-Architecture/-A1-7-Reliability--Availability--and-Serviceability/-A1-7-3-General-taxonomy-of-errors?lang=en#mdterm_ras_poisoned) from a Location, see [Use of the RAS Extension](/documentation/ddi0487/mc/-Part-K-Appendixes/-Appendix-K10-Software-Usage-Examples/-K10-7-Use-of-the-RAS-Extension?lang=en#mdsec_use_of_the_ras_extension).

I PSLGW
:   In order to test that [poison](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A1-Introduction-to-the-Arm-Architecture/-A1-7-Reliability--Availability--and-Serviceability/-A1-7-3-General-taxonomy-of-errors?lang=en#mdterm_ras_poisoned) has been removed from a Location, after the Location has been overwritten by a known-good value, software must be able to read back the Location from physical memory to check that the [poison](/documentation/ddi0487/mc/-Part-A-Arm-Architecture-Introduction-and-Overview/-Chapter-A1-Introduction-to-the-Arm-Architecture/-A1-7-Reliability--Availability--and-Serviceability/-A1-7-3-General-taxonomy-of-errors?lang=en#mdterm_ras_poisoned) has been removed and the error is not persistent.

    To do this, software must ensure that the Location has been cleaned and invalidated from all caches, so that the read returns a value from the [Point of Physical Storage](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D7-The-AArch64-System-Level-Memory-Model/-D7-5-Cache-support/-D7-5-8-About-cache-maintenance-in-AArch64-state?lang=en#mdterm_point_of_physical_storage) for the Location, and not any intermediate cache.

    The [Point of Coherency](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D7-The-AArch64-System-Level-Memory-Model/-D7-5-Cache-support/-D7-5-8-About-cache-maintenance-in-AArch64-state?lang=en#beifcdgi) might be before a transparent unified cache, meaning that it might be before the [Point of Physical Storage](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D7-The-AArch64-System-Level-Memory-Model/-D7-5-Cache-support/-D7-5-8-About-cache-maintenance-in-AArch64-state?lang=en#mdterm_point_of_physical_storage) for a Location.

    For more information on the [Point of Physical Storage](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D7-The-AArch64-System-Level-Memory-Model/-D7-5-Cache-support/-D7-5-8-About-cache-maintenance-in-AArch64-state?lang=en#mdterm_point_of_physical_storage), see [A64 Cache maintenance instructions](/documentation/ddi0487/mc/-Part-D-The-AArch64-System-Level-Architecture/-Chapter-D7-The-AArch64-System-Level-Memory-Model/-D7-5-Cache-support/-D7-5-9-A64-Cache-maintenance-instructions?lang=en#chdbfich).
