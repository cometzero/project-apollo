# QBox Apollo FVP Full-System Goal And Verification

Generated: 2026-06-03

Status: final verified

## Goal

The full-system task proves that QBox can boot the local Apollo FVP artifacts
through the same subsystem chain expected from the Arm FVP:

```text
RSE TF-M -> SI CL0 SCP-firmware -> SI CL1 Zephyr -> AP TF-A/OP-TEE/U-Boot/Linux
```

The target is not "Linux reaches a shell". The target is one integrated
QBox run where RSE, Safety Island CL0, Safety Island CL1, and Primary Compute
are all live and the saved evidence shows that cross-domain firmware handoff,
interrupt routing, ATU/ATW visibility, MHU/SCMI/HIPC/PFDI paths, and AP Linux
post-login probes are either passing or explicitly classified by the gate.

## Acceptance Target

The full-system task is complete only when the canonical live full-system
evidence directory passes strict verification:

```text
build/qbox-apollo-fvp/full-live-cl0-cl1/final-verification.json
```

That file must be generated by
`scripts/test/verify_qbox_apollo_fvp_full_completion.py --strict-final`, the command
must exit 0, and the JSON must authorize completion with
`completion_claim_allowed: true`. A successful QBox process launch, a Linux
login prompt, an isolated Safety Island boot, or a non-strict progress verdict
is not an acceptance target.

## Non-Completion Points

These are useful milestones, but they must not be reported as full-system
completion:

| Evidence | Why it is not enough |
| --- | --- |
| Direct AP Linux boot reaches login | Bypasses RSE, TF-A, OP-TEE, U-Boot, SI CL0, SI CL1, SCMI, PFDI, and GIC multiview. |
| RSE-first service-model run reaches Linux | Proves AP firmware path progress but keeps live Safety Island CPU fidelity debt. |
| Isolated SI CL0 or SI CL1 firmware boots | Proves Cortex-R82 firmware bring-up only, not AP/RSE/SI integration. |
| `live-cl1` AP integration passes | Proves Zephyr and AP HIPC/RPMsg path while CL0 SCP-firmware remains modeled. |
| tmux screen output only | Has no durable `result.json`, per-UART logs, marker groups, or blocker classification. |

## Completion Gates

The verifier uses six gates. All six gates are mandatory for final completion.

| Gate | Name | Completion role | Required evidence |
| --- | --- | --- | --- |
| G0 | Contract readiness | Required precondition. | Local artifacts resolve, Cortex-R82 support builds, map validator passes, coverage audit contract exists. |
| G1 | Direct-boot guardrail | Required regression guardrail. | Existing `scripts/run/run_qbox_apollo_fvp_linux.py` still reaches login and post-login probes. |
| G2 | Service-model full boot | Required milestone, not final completion. | RSE-first service-model run reaches AP Linux and records service-model debt. |
| G3 | Live CL1 integration | Required milestone, not final completion. | Live CL1 Zephyr and AP Linux HIPC/RPMsg/PFDI markers pass with CL0 debt still explicit. |
| G4 | Live CL0/CL1 integration | First runtime completion candidate. | RSE, CL0 SCP-firmware, CL1 Zephyr, AP firmware, U-Boot, Linux, and post-login marker groups pass in one run. |
| G5 | FVP equivalence closure | Final acceptance gate. | FVP comparison, normalized map/interrupt/ATU comparison, and hardware coverage audit pass with no unclassified boot-critical gap. |

`G4` is the first point where the runtime shape can be considered a completion
candidate. `G5` is the point where that candidate becomes acceptable.

## Final Evidence Bundle

The only accepted final bundle is:

```text
build/qbox-apollo-fvp/full-live-cl0-cl1/
  result.json
  comparison.json
  map-comparison.json
  coverage-audit.json
  final-verification.json
```

The bundle is complete only when:

- `result.json` records `verdict: "pass"`, `safety_island_mode:
  "live-cl0-cl1"`, all required marker groups, file-backed subsystem logs, the
  command used for the run, and the runtime gates required for the final live
  run: `completion_gates.G0 == "pass"` and
  `completion_gates.G4 == "pass"`.
- `result.json` records `platform_observations.ap_cpus == 4`,
  `secure_console_observations.ap_bl2_console == true`,
  `secure_console_observations.bl31_console == true`,
  `secure_console_observations.optee_console == true`, and
  `primary_console_observations.u_boot_console == true`. RSE measured-boot
  evidence for AP firmware images alone is not sufficient, because RSE can
  measure AP images before the corresponding AP firmware stage executes.
- `comparison.json` records that required FVP boot markers are present in the
  QBox run, with no unclassified missing marker.
- `map-comparison.json` records AP, RSE, SMD, SI CL0, and SI CL1 memory,
  interrupt, and ATU/ATW views as passed or reviewed.
- `coverage-audit.json` records every boot-critical hardware block as live,
  accepted service-modeled debt, or accepted register-stub debt. An absent
  boot-critical block is a failure.
- `final-verification.json` is produced by the strict verifier in the same
  directory.

If any gate is `blocked`, `fail`, or `not_run`, the correct project verdict is

The strict verifier also rejects final completion when any of these details are
missing even if a run produced console output:

- the final run directory is not the canonical
  `build/qbox-apollo-fvp/full-live-cl0-cl1/`;
- `result.json` is not a passing `live-cl0-cl1` run;
- any required sidecar artifact is absent from the final bundle;
- sidecar artifacts exist but do not report `passed: true`;
- AP BL2, BL31, OP-TEE, U-Boot, Linux, RSE, SI CL0, or SI CL1 execution is
  inferred rather than proven by file-backed logs and marker groups;
- `first_incomplete_gate`, `first_blocker`, or
  `completion_rejection_reason` is set.

The verifier also records the first rejection point for review automation:

| Field | Meaning |
| --- | --- |
| `first_incomplete_gate` | First G0-G5 gate that is not `pass`. |
| `gate_blockers` | Gate-to-blocker map for accepted `blocked` classifications. |
| `first_blocker` | The blocker or failed check that prevents a completion claim. |
| `completion_rejection_reason` | Alias of the same human-readable rejection reason. |

For final completion, `first_incomplete_gate`, `first_blocker`, and
`completion_rejection_reason` must all be `null`. If any of them is set, the
review decision is progress, blocked, or failed, not complete.

## Review Decision Procedure

Use this procedure when deciding whether the full-system task can be closed:

1. Check the final run directory is the canonical
   `build/qbox-apollo-fvp/full-live-cl0-cl1/`; ad-hoc trace directories are
   progress evidence only.
2. Open `result.json` and confirm `safety_island_mode` is `live-cl0-cl1`,
   `verdict` is `pass`, `completion_gates.G0 == "pass"`,
   `completion_gates.G4 == "pass"`, and `first_failing_marker` is `null`.
3. Confirm AP execution was real, not inferred from RSE image loading:
   `platform_observations.ap_cpus == 4`,
   `secure_console_observations.ap_bl2_console == true`,
   `secure_console_observations.bl31_console == true`,
   `secure_console_observations.optee_console == true`,
   `primary_console_observations.u_boot_console == true`, and AP firmware
   markers include BL2, BL31, OP-TEE, and U-Boot.
4. Confirm all raw subsystem logs are file-backed and non-empty: platform, RSE,
   SI CL0, SI CL1, secure AP firmware, and primary AP console.
5. Run G5 sidecar checks in the same directory:
   `comparison.json`, `map-comparison.json`, and `coverage-audit.json` must all
   report `passed: true`.
6. Run the strict verifier and require exit status 0:
   `completion_claim_allowed == true`, `completion_ready == true`, and
   `overall_gates.G0..G5 == "pass"`.
7. Confirm `first_incomplete_gate == null`, `first_blocker == null`, and
   `completion_rejection_reason == null` in `final-verification.json`.

If any step fails, the correct review verdict is `blocked` or `fail`, not
complete. The report must name the first missing marker, missing artifact, or
fidelity gap from the machine-readable output.

## Failure Classification

Every failing run must keep the first failure machine-readable:

| Verdict | Required use |
| --- | --- |
| `pass` | Gate command exited successfully and every required marker/audit/comparison check passed. |
| `blocked` | A specific missing model, missing artifact, host dependency, or known fidelity gap prevents progress. |
| `fail` | A required marker, map, interrupt, coverage, or comparison check failed without an accepted gap classification. |
| `not_run` | The gate was intentionally skipped; final completion cannot be claimed. |

The final report should cite the evidence directory, the exact commands run,
and the first blocker or missing marker if completion is rejected.
